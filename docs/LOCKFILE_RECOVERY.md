# Lockfile recovery and dependency reproducibility

## Current state

The source archive does not contain a legitimate `pnpm-lock.yaml`. This is a release blocker. A lockfile must be generated by pnpm from the declared manifests on a registry-enabled Node 24 host; it must never be fabricated or hand-edited.

## Controlled recovery procedure

1. Use a clean, disposable checkout.
2. Install Node 24 and activate the repository-pinned pnpm version.
3. Confirm no unreviewed `.npmrc`, proxy, registry, or lifecycle-script override is present.
4. Generate only the lockfile.
5. Review the complete dependency diff.
6. Run a frozen install from a second clean checkout.
7. Execute the full validation and security pipeline.
8. Commit the lockfile and recorded evidence together.

```bash
node --version
corepack enable
corepack prepare pnpm@10.14.0 --activate
pnpm --version
pnpm install --lockfile-only
node scripts/ci/check-lockfile.mjs
```

Review at minimum:

- unexpected registries or tarball URLs;
- git dependencies;
- packages with install scripts;
- peer-dependency conflicts;
- duplicate major versions of security-sensitive libraries;
- native modules and prebuilt binaries;
- license-policy violations;
- known vulnerabilities and malicious-package alerts.

Then prove reproducibility:

```bash
git clean -xffd
pnpm install --frozen-lockfile
pnpm validate
```

## Required evidence

A release record must include:

- Node and pnpm versions;
- lockfile checksum;
- frozen-install output from a clean checkout;
- dependency, license, secret, SAST, and SBOM scan artifacts;
- test, build, browser, database, container, and restore results tied to the same commit.

## Prohibited shortcuts

Do not:

- run production installs without `--frozen-lockfile`;
- accept an automatically generated lockfile without review;
- weaken CI to permit a missing or changed lockfile;
- hand-create package resolutions;
- copy a lockfile from another branch or repository;
- call the source reproducible until a second clean frozen install succeeds.
